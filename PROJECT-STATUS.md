> **Strategic direction note (Session 190):** Highlander Today should now be treated as the first flagship tenant and proving ground of the broader SivicOS platform architecture rather than as a standalone local-news product. SivicOS is now the parent platform/company direction for the ecosystem, with Highlander Today acting as the first civic/media/community implementation and operational pilot. The broader long-term direction includes reusable geographic knowledge systems, tenant-aware civic infrastructure, trust systems, AI-assisted editorial workflows, streaming/media systems (`Mode B`), local event/ticketing infrastructure, and future community/organization tooling built around geography as a first-class entity model rather than simple category tagging. New architectural planning and long-range platform positioning should increasingly separate:
>
> - `SivicOS` → parent platform/infrastructure/provider layer
> - `Highlander Today` → first flagship civic/community tenant
> - `Mode B` → streaming/broadcast/media layer
>
> Geographic entities (boroughs, townships, counties, school districts, service areas, etc.) should increasingly be treated as foundational entities to which governments, organizations, events, alerts, local knowledge, utilities, and media feeds attach.
>
> See `SIVICOS-PLATFORM-VISION.md` for the current high-level platform framing and long-term architectural direction.

> **Session 210 reporter authenticated-browser note:** the local browser-collector architecture now looks like the likely long-term answer for at least one major class of source-ingestion problems: sites that block cloud/server scraping, render behind heavy JavaScript, embed third-party widgets, or only expose useful content to a normal residential browser session. This does not automatically make every source easy or safe, but it materially changes feasibility. Future design should assume distinct reporter ingestion lanes rather than one generic scraper: (1) public structured sources, (2) public browser-rendered sources, (3) authenticated browser-rendered sources, and (4) high-risk/manual-review-required sources. With valid accounts, the local persistent-browser approach could plausibly support login-gated sources such as paywalled outlets or private/community pages, but those should be treated as a separate higher-risk product lane with explicit per-source enablement, stronger audit logging, session/cookie persistence, and a conservative workflow that seeds leads/source packets rather than trusting direct autonomous publication. Facebook-class sources in particular should be considered technically possible but operationally fragile and policy-sensitive because of MFA/checkpoints, anti-automation detection, rate limits, account-risk concerns, and terms-of-service ambiguity. If/when this lane is pursued, design discussion should focus first on authorization/accountability and source-policy boundaries, not only on extraction mechanics.
