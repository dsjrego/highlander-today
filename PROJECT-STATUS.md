# Highlander Today — Project Status

> **Last updated:** 2026-05-23 (session 190)
> **Purpose:** Fast-start context for the next session. Read this file first, then open only the supporting docs relevant to the active slice.
> **Detailed reference:** `PROJECT-STATUS-REFERENCE.md` preserves the fuller implementation ledger, rollout history, verification notes, deployment runbook, and infrastructure rationale that used to live here.

> **Strategic direction note (Session 190):** Highlander Today should now be treated as the first flagship tenant and proving ground of the broader SivicOS platform architecture rather than as a standalone local-news product. SivicOS is now the parent platform/company direction for the ecosystem, with Highlander Today acting as the first civic/media/community implementation and operational pilot. The broader long-term direction includes reusable geographic knowledge systems, tenant-aware civic infrastructure, trust systems, AI-assisted editorial workflows, streaming/media systems (`Mode B`), local event/ticketing infrastructure, and future community/organization tooling built around geography as a first-class entity model rather than simple category tagging. New architectural planning and long-range platform positioning should increasingly separate:
>
> - `SivicOS` → parent platform/infrastructure/provider layer
> - `Highlander Today` → first flagship civic/community tenant
> - `Mode B` → streaming/broadcast/media layer
>
> Geographic entities (boroughs, townships, counties, school districts, service areas, etc.) should increasingly be treated as foundational entities to which governments, organizations, events, alerts, local knowledge, utilities, and media feeds attach.
>
> See `SIVICOS-PLATFORM-VISION.md` for the current high-level platform framing and long-term architectural direction.

> **Recipe system note:** the first dedicated recipe domain is now live. Recipes are no longer just an article-body styling experiment; Prisma now includes first-class recipe tables, structured JSON/form ingest, recipe-specific admin moderation, section/category support through `CategoryContentModel.RECIPE`, and a dedicated homepage recipe lane. The older `editorial-recipe.css` and HTML-import work should still be treated as temporary bridge/presentation work for editorial content, not as the long-term persistence model for recipes.

> **Reporter system note:** the reporter foundation is now materially complete for the current intended slice. Public intake, internal reporter-run management, source/blocker CRUD, bounded draft generation, convert-to-article flow, `SOURCE_PACKET_SUMMARY` analysis, and the browser-based interview loop are all live and have now received real-world editorial QA. Treat the current reporter system as working rather than as an active unfinished build; remaining reporter work is primarily documentation hygiene, future-slice planning, and any later product refinements the user explicitly chooses to pursue.

> **Session 184 note:** Memoriam now has its first moderated community-memory loop. Published memorial detail pages show approved memories and include a trusted-user-only `Share a Memory` form; submissions write `MemorialMemory` rows in `PENDING` status rather than public comments. `/admin/memoriam` now includes a memory moderation table, and `/api/memoriam/memories/[id]` lets staff approve, reject, or hide memory submissions. Current boundary: photo contribution, steward self-service approval, and richer memory editing/notification flows are still future slices.

> **Session 186 note:** Memoriam is now substantially complete for a real community launch. This session covered two passes: (1) submission form UX — age is now auto-calculated from birth/death dates instead of requiring a hard entry, "Factual summary" and "Short memorial summary" labels dropped "summary," both those fields gained character limits (1,000 and 300 chars respectively) with live counters and validation, "Provenance note" became "Where this information comes from" with a plain-language description, and the confusing "stays under review" copy in the What happens next panel was corrected; (2) media and stewardship — multi-photo upload (up to 20 photos, R2-backed, new `memoriam` upload context) added to the submission form with per-photo captions, YouTube/Vimeo embed URL fields (up to 5) and a memorial service stream link added, `MemorialPage` schema gained `videoEmbeds String[]` and `serviceStreamUrl String?`, photo gallery and video embed rendering added to the public memorial detail page, the `MEMORIAM` value added to `HomepageBoxType` with homepage rendering wired to `RecentlyRemembered`, a full steward self-service manage page built at `/memoriam/[slug]/manage` (edit text, manage photos/videos, approve memories, invite co-stewards), admin steward assignment and inline photo approval added to `/admin/memoriam`, and five new API route families added (`/api/memoriam/pages/[id]/photos`, `/api/memoriam/photos/[id]`, `/api/memoriam/pages/[id]/contributors`, `/api/memoriam/pages/[id]/manage`). Schema changes require `prisma db push` before deployment.
