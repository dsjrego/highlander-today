> **Strategic direction note (Session 190):** Highlander Today should now be treated as the first flagship tenant and proving ground of the broader SivicOS platform architecture rather than as a standalone local-news product. SivicOS is now the parent platform/company direction for the ecosystem, with Highlander Today acting as the first civic/media/community implementation and operational pilot. The broader long-term direction includes reusable geographic knowledge systems, tenant-aware civic infrastructure, trust systems, AI-assisted editorial workflows, streaming/media systems (`Mode B`), local event/ticketing infrastructure, and future community/organization tooling built around geography as a first-class entity model rather than simple category tagging. New architectural planning and long-range platform positioning should increasingly separate:
>
> - `SivicOS` → parent platform/infrastructure/provider layer
> - `Highlander Today` → first flagship civic/community tenant
> - `Mode B` → streaming/broadcast/media layer
>
> Geographic entities (boroughs, townships, counties, school districts, service areas, etc.) should increasingly be treated as foundational entities to which governments, organizations, events, alerts, local knowledge, utilities, and media feeds attach.
>
> See `SIVICOS-PLATFORM-VISION.md` for the current high-level platform framing and long-term architectural direction.

> **Session 191 reporter maturity note:** the reporter-agent maturity epic is now functionally complete inside the existing application stack. Reporter runs now have durable `ReporterAgentTask`, `ReporterAgentTrace`, and `ReporterClaim` records; prompt files and stable prompt hashing are live; interview-next-step and draft-generation model outputs are schema-validated and traced; deterministic fallback paths are auditable; manual internal triage can be triggered from the reporter run detail screen; a deny-by-default reporter-agent permission policy blocks publish/contact/browse actions; claims are created from reviewed interview facts and source-packet analysis; and the admin run detail page now exposes an `Agent` tab with tasks, traces, claims, inline claim verification updates, and triage visibility. Remaining reporter work should be treated as future refinement or roadmap work rather than unfinished foundation.

> **Session 192 reporter daily-coverage note:** the first implementation slice of `REPORTER-DAILY-COVERAGE-ROADMAP.md` Epic 1 is now live. Prisma now includes tenant-aware monitoring foundations for recurring local sources: `ReporterMonitoredSource`, `ReporterSourceFetch`, and `ReporterSourceIngestionItem`, plus the supporting enums and `ActivityLog` resource types. Internal admin tooling now includes `/admin/reporter/sources`, a reporter source-monitor registry for the current tenant with source health visibility, coverage-place scoping, fetch cadence, recent fetch summaries, and active/pause/archive controls. Admin APIs now exist under `/api/admin/reporter/monitored-sources/*` for creating/updating source registry entries and recording normalized fetch results/items, and the new ingestion service deduplicates items per source while tracking `new` versus `changed` records and updating source-level fetch/health timestamps. This is intentionally only the Epic 1 foundation slice: there is still no scheduled fetch runner, no real external feed parser/fetch executor, no story-candidate clustering/ranking, and no daily production orchestrator yet. Environments receiving this slice need `npx prisma db push --schema prisma/schema.prisma` before the new monitoring tables can be used. Verification passed with `npm run typecheck`, `npm run lint`, and targeted reporter unit tests for the monitored-source routes and ingestion service.
>
> **Session 193 reporter fetch note:** Epic 1 now has its first real public-source fetch/extraction pass. `src/lib/reporter/public-source-fetcher.ts` can now execute on-demand public fetches for monitored `RSS`, `ATOM`, `JSON`, and `HTML` sources, reuse conditional request headers (`ETag` / `Last-Modified`) when available, normalize parsed items into the existing ingestion model, and record `SUCCESS`, `NO_CHANGE`, or `FAILED` fetch results through the shared ingestion service. `/api/admin/reporter/monitored-sources/[id]/run-fetch` now triggers that executor for the current tenant, and `/admin/reporter/sources` now exposes a per-source `Fetch now` action so staff can exercise public-source monitoring without waiting for a future scheduler. Current boundary: this is still on-demand only, parser coverage is intentionally modest, and `PDF`, `ICS`, and other unsupported formats still fail closed rather than attempting brittle extraction. Verification passed with `npm run typecheck`, `npm run lint`, and targeted reporter unit tests including the new public-source fetcher/service coverage.
>
> **Session 194 reporter scheduler note:** Epic 1 now has its first bounded due-source runner. `src/lib/reporter/monitored-source-scheduler.ts` can now select `ACTIVE` monitored sources whose fetch window is due for a given tenant and execute them sequentially through the existing public-source fetcher, returning a compact success / no-change / failure summary rather than behaving like a long-running worker. `/api/admin/reporter/monitored-sources/run-due` now exposes that runner as a short-lived trigger surface: authenticated internal editorial users can run the current tenant’s due sources from the admin UI, and the route also supports an optional bearer token path through `REPORTER_SCHEDULER_TOKEN` when a deployment scheduler later needs to call it with explicit tenant scope. `/admin/reporter/sources` now includes a `Run Due Sources` action with inline result feedback. Current boundary: there is still no persistent background process, no cross-tenant global orchestrator, and no durable queued job layer for source fetches; this slice intentionally remains a cron-friendly one-pass runner inside the existing application stack. Verification passed with `npm run typecheck`, `npm run lint`, and targeted reporter unit tests including the new scheduler/service and route coverage.
